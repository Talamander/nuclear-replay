# Network demos: record and cinematic replay

This is the working record/replay path. It replaces the per-frame visual capture approach for cinematic playback. Visual capture stays off.

## How it works

**Recording (NuclearReplay.dll 0.4.0, `src/Demo/`).** When a mission is hosted, the recorder adds an invisible spectator connection to the game's own Mirage server. The server treats it like a remote multiplayer client. It sends the spectator everything a remote player would receive: spawns, transform batches, SyncVar updates, RPCs (launches, hits, damage, kills, detonations), destroys and mission state. The recorder writes each outgoing message with its timestamp to a `.ncdemo` file on a background thread. It never reads Unity objects or scans the scene, so its cost is about the same as one extra multiplayer client.

Single-player needs three small patches, which apply only while the ghost connection exists:

- The ghost receives the mission through `NetworkMission.Set`, because single-player does not publish it otherwise.
- `SendTransformBatcher.ServerUpdate` runs, because it is otherwise limited to multiplayer.
- `CrashAircraftObjective.GetTotalLives` does not count the ghost as a player with lives.

The recorder adds no AI, physics or damage of its own. The ghost has no aircraft and sends no input.

**Replay (the player plugin in NuclearReplay.dll, `replay/`).** Launch the game with `-ncReplay <file>`. After the main menu loads, the game starts as an ordinary multiplayer client. Its socket connects to an in-memory stand-in host, which sends the recorded messages back on the recorded clock. The client loads the map, spawns the units and plays the effects with its own code and assets. Outcomes come from the recording: who fired, what hit, what was damaged and what died. The client makes no AI, physics or damage decisions for other units.

Cosmetic effects such as smoke, sparks and debris are generated by the client's effect code. They can differ slightly from the original session. Gun tracers and impact particles are an example.

`NetworkTime.Time` reports the recorded server time. Transform interpolation uses the replay clock, so pause and speed changes stay consistent. The stand-in host waits while the client loads a scene, as the real host does, and answers pings.

**Director (`replay/src/Director.cs`).** The director drives the game's own camera system (`CameraStateManager`) from a JSON shot list.

## Usage

Recording is automatic for every hosted mission while `[Demo] Enabled = true` (the default). Files go to `[Demo] OutputDirectory`, which defaults to `<game>/NuclearReplay/demos/<UTC>-<mission>.ncdemo`. Recordings use about 10 KiB/s, or 36 MB per hour, for the Furball mission.

The recorder also writes gameplay events into the demo as annotation records (format in `docs/PRODUCT-CONTRACT.md` §1). They come from hooks the game already calls, so they add no scene scans and no per-frame work:

- `mission`: mission name and map, once at the start.
- `player`: a human player, again each time they spawn an aircraft (`unit`).
- `launch`: shooter, target, weapon and the missile's unit id.
- `kill`: victim, killer and weapon, from the game's own kill feed. `killer` is null for crashes. `weapon` is null when no damage call named it. Since 0.5.1, `hit_ago` gives the seconds from the killer's last weapon hit on the victim to the kill feed (missing when there was none). The viewer and `nr` place the kill at the hit.

Example from a Furball recording:

```json
{"t": 27.608, "event": "kill", "victim": {"id": 138, "name": "Talamander [T/A-30 Compass]", "type": "aircraft", "faction": "Boscali", "player": "Talamander"}, "killer": {"id": 128, "name": "T/A-30 Compass", "type": "aircraft", "faction": "Primeva"}, "weapon": "MMR-S3"}
```

The heavy telemetry bundle (events, states and motion samples in `<game>/NuclearReplay/<UTC>-<id>/`) is separate from the demo. `[Capture] TelemetryBundle` turns it on or off. Demo recording and the events work with the bundle off.

- A new install (no config file yet) gets `TelemetryBundle = false`: demos only.
- An existing config gets `TelemetryBundle = true` added, so it keeps its current behaviour.
- `-ncTelemetryBundle on|off` overrides the setting for one game session.

Inspect a demo:

```
python3 tools/demo_inspect.py "<game>/NuclearReplay/demos/<file>.ncdemo"
python3 tools/demo_inspect.py --events "<game>/NuclearReplay/demos/<file>.ncdemo"
```

The first form prints the header, the message mix and each annotation in readable form. `--events` prints only the annotations, one JSON object per line, each with `"t"` in replay seconds (for a kill, the kill feed) and, for kills with `hit_ago`, `"hit_t"`.

Watch a replay interactively by adding launch options for one session. The window opens normally:

```
-ncReplay /path/to/file.ncdemo [-ncShots /path/to/shots.json]
```

Config files: the recorder uses `BepInEx/config/talamander.nuclearreplay.recorder.cfg` and the replay plugin
`talamander.nuclearreplay.player.cfg`. Earlier versions used other GUIDs, and so other file names:
`talamander.nuclearcontext` / `talamander.nuclearcontext.replay` (Nuclear Context betas) and, before
that, `local.nuclearoption.context` / `local.nuclearoption.context.replay`. On its first start each
plugin copies the newest old file that exists to the new name when the new one does not exist yet;
the old files stay.

Use these keys during replay. They are active only while a replay runs, and all are configurable in `BepInEx/config/talamander.nuclearreplay.player.cfg`:

- Pause: pause or resume.
- PageUp: double the speed, up to 8x.
- PageDown: halve the speed, down to 1/8x.
- Home: follow the next aircraft.
- End: cycle the orbit, chase, cockpit, TV and free cameras.
- Insert: show or hide the status overlay.
- Delete: show or hide the game HUD.

### In-game replay viewer

`-ncViewer` turns a replay into the in-game viewer: the game itself shows the match at full quality,
with sound, and records clips. The game's **Replays** button and `nr open <demo> [--at s] [--focus s]`
start it (docs/AGENTS.md).

```
-ncReplay <demo> -ncViewer [-ncAt <s>] [-ncFocus <s>] [-ncClipsDir <dir>] [-ncFfmpeg <exe>] [-ncQuality N] [-ncEncoder auto|nvenc|vulkan|x264]
-ncViewer                      # no recording: the main menu with the Replays list open
```

- The main menu gets a **Replays** button next to the game's own buttons. It lists the recordings in
  `<game>/NuclearReplay/demos` (mission, map, date, length, players, kills, launches). Double-click
  or **Watch** opens one. **Exit** in the viewer goes back to the menu with the list open.
- The overlay (uGUI, `replay/src/ViewerUi.cs`) has a timeline with launch (amber) and kill (red)
  markers, the clip window (blue) and a playhead. A click jumps; a click on a marker jumps to that
  moment and sets the clip in and out points to 5 s before and 6 s after it.
- Keys: Space play/pause, Left/Right 10 s, Up/Down or +/- speed (0.25x to 4x), 1 to 8 camera presets
  (the camera styles of `nr render`, `ViewerPresets.cs`), [ and ] previous and next aircraft, F free camera
  (WASD, Q/E, Shift, wheel for speed, Ctrl + wheel to zoom, hold the right mouse button to look), P Camera
  Studio, I/O clip in and out, C record the clip, G the game's HUD, H hide all UI, F1 help, Backspace back
  to the menu.
- **Camera Studio** (P, or **Camera path** in the bottom bar; `replay/src/ReplayPlugin.Studio.cs`,
  model `CameraStudio.cs`) lays down a camera path with the free camera. K adds a key at the free camera's
  pose, lens and the replay's time, after the selected key. A key laid while the replay stands still goes
  3 s after the one before it; one laid after the replay moved on takes the replay's time. U moves the
  selected key to the free camera's pose (its time stays), X or Delete deletes it, [ and ] select a key and
  put the free camera on it, comma and period move the selected key and every later key 0.5 s. T switches
  timing (even speed or reach every key at its time), L the aim (the keys' own view, look at the aircraft,
  look along the path), J the shake (off, handheld, heavy handheld, rumble, buffet) and M the space (world,
  or moving with the aircraft that was followed when the studio opened; every key needs that aircraft alive).
  Enter plays the path from 1.5 s before its first key and goes back to the free camera 1 s after the last;
  C clips exactly that span. The panel shows the keys and settings, the timeline shows the path's span
  (purple) and a tick per key, and the path is drawn into the scene with a numbered dot per key while
  editing. Every change saves `<demo>.path.json` beside the recording: a shot list with the one `path` shot
  (so `-ncShots` and render jobs can use it) plus the studio's own keys, which load the next time the studio
  opens on that recording. Deleting the recording deletes it too.
- Jumps forward fast-forward in fixed 8/60 s steps. Jumps back restart the mission and fast-forward
  from the start (docs/JUMP-POINTS.md has the measured times and a plan for faster jumps).
- The game's green flight HUD and its bottom unit panel (speed, altitude, weapons) are hidden unless
  G turns them on.
- Free camera under Proton: with an unlocked cursor Wine sends only absolute pointer motion, so mouse
  deltas read zero. The cursor is locked and hidden while the right button is held, and the look falls
  back to the change in cursor position when deltas still read zero.
- **Clip this** (C) plays the in/out range at 1x in real time and encodes the screen at its native
  resolution, 60 fps, without UI. Frames come through an asynchronous GPU readback. Game audio comes
  from the audio listener (`OnAudioFilterRead`), so it records even when the session is muted.
  Encoders: `auto` tries `h264_nvenc`, `h264_vulkan`, then `libx264`. Under Proton `h264_nvenc` does
  not start; `h264_vulkan` encodes on the GPU through winevulkan. The clip goes to `-ncClipsDir`
  (default `<game>/NuclearReplay/clips`), named `<mission> m-ss to m-ss.mp4` with ` (2)` and up on a
  collision (`shared/Clips/ClipNames.cs`). Each clip also writes
  `<game>/NuclearReplay/viewer-clips/<UTC>-<id>/job.json` (the render job format with
  `"source":"viewer"`) and `progress.json`, which also has `encoder`, `fps_before`, `fps_during` and
  `audio`. Nothing in this repository reads these folders now (the desktop app imported them); scripts
  can.
- `[Viewer]` in `talamander.nuclearreplay.player.cfg` keeps the last clips folder, ffmpeg path,
  quality and encoder, so launches from the game's own Replays menu use them too. `nr install` fills
  `FfmpegPath` and `ClipsDirectory` there when they are missing or empty. With both empty the viewer
  asks before it downloads ffmpeg into `<game>/NuclearReplay/tools/ffmpeg` and saves clips to
  `<game>/NuclearReplay/clips`.
- Test hook: `-ncViewerCommands <file>` (or `NC_VIEWER_COMMANDS`) runs one command per line appended to
  the file (`menu-button`, `menu-pick`, `menu-watch`, `seek`, `skip`, `speed`, `preset`, `unit`,
  `free`, `fly`, `look`, `hide`, `help`, `toast`, `gamehud`, `in`, `out`, `clip`, `moment`, `timeline`, `shot`,
  `studio on|off|key|update|delete|select <n>|play|stop|timing|aim|shake|space|retime <s>|clip|clear`,
  `exit`, `quit`, and `msgstats`, `uiat` for research) and writes `<file>.status` (JSON, with a `studio`
  object) every 0.5 s.
  Headless screenshots use `shot <png>`.

Render a clip off-screen and silent to MP4. This needs Steam running and the game closed:

```
scripts/render-clip.sh demo.ncdemo 40 48 out.mp4 [shots.json] [fps]
```

The script runs the game in a headless gamescope session. It exports exactly one PNG per 1/fps of replay time (Unity `captureFramerate`), hides the HUD and fast-forwards at 4x to the start of the range. Then it encodes the frames with ffmpeg and deletes them.

Render many ranges in one game run with `scripts/render-clips.sh`. This is the fast path used for Shorts (details and measurements in `/mnt/games/nuclear-option-content/2026-10-01-confrontation/SPEEDUP.md`):

```
scripts/render-clips.sh demo.ncdemo "1929:1952,1953:1988,1992:2004@60" outdir [shots.json] [fps]
```

- The default fps is 30. Add `@60` to a range to render only that range at 60 fps.
- The plugin streams raw frames (`-ncFrameFormat raw`) through one FIFO per range into ffmpeg, so there are no PNG files. Each range is encoded while the game continues to the next range.
- The encoder is `h264_nvenc` (CQ 19) when available, otherwise x264 veryfast CRF 16. Set `ENCODER=x264` to force x264.
- The skip to each range uses fixed 8/60 s replay steps (`FAST_FORWARD="8 60"`), not the 4x wall-clock speed. 16/60 steps change which missile the `auto` camera follows.
- Overlapping ranges are rendered once and cut apart afterwards.
- Clips are cached in `RENDER_CACHE` (default `/mnt/games/nuclear-option-content/render-cache`). The cache key covers the demo, range, fps, size, the shots in effect, the plugin DLL, the skip setting and the encoder. Set `NO_CACHE=1` to skip the cache.
- `RENDER_MODE=legacy` runs the old path exactly: PNG frames, 4x skip and x264 slow after the game exits (`scripts/render-clips-legacy.sh`).
- `scripts/render-batch.py jobs.json [--dry-run]` packs the ranges of several Shorts into as few game runs as their shot lists allow, then delivers each Short's clips from the cache.

Render without a shell script with `-ncRenderJob <job.json>`. This is the path `nr render` uses, and the one for native Windows. The job format is in `docs/PRODUCT-CONTRACT.md` §2. All paths in the job must be paths the game can open. Under Proton, write `/mnt/x/y` as `Z:\mnt\x\y`.

```
scripts/run-headless.sh -ncRenderJob 'Z:\path\to\job.json'
```

- The plugin renders every range of the job in one game run, then quits.
- It starts the job's `ffmpeg` itself and pipes raw RGBA frames into its stdin. Each clip is written as `<out>.part` and renamed when ffmpeg finishes.
- `encoder`: `auto` tries `h264_nvenc`, then `h264_vulkan`, and falls back to `libx264`; `nvenc`, `vulkan` or `x264` forces one. `quality` is the CQ or CRF value (default 19). Vulkan uses constant QP `quality + 1`.
- The skip, preroll, readback and HUD hiding are the same as `render-clips.sh` (fixed 8/60 s steps unless `-ncFastForward` is given).
- `progress` is rewritten atomically: `{"state", "range", "ranges", "frame", "frames", "error", "encoder"}`. States are `loading`, `seeking`, `rendering`, `encoding`, then `done` or `error`.
- The job fails with state `error` and a message when the job is invalid, ffmpeg fails, a range runs past the end of the demo, or the replay is not live within 900 s. Clips that finished before the error stay.
- Ranges must not overlap; the job is rejected if they do. Engine mattes are not written in job mode.
- `"vflip": true|false` in the job overrides the automatic vertical flip. The default is right for Proton.
- Under Proton, use a Windows ffmpeg build (for example the one `nr ffmpeg install` downloads). In testing, `h264_nvenc` did not start inside Proton (ffmpeg exits with -1), but `h264_vulkan` works through Wine's Vulkan, so `auto` uses `h264_vulkan` (checked 2026-10-10 for a headless render job and for Clip this). If no GPU encoder starts, `auto` uses `libx264`.

Other replay options:

- `-ncReplayFrames <dir> [fps]`: export frames.
- `-ncCaptureRange <from> <to>`: limit the frame export to a range.
- `-ncReplayShots <dir> <seconds>`: take a periodic screenshot.
- `-ncNoHud`: hide the HUD.
- `-ncFrameFormat png|raw`: `raw` appends RGBA frames to `<range dir>/frames.rgba` (a FIFO in `render-clips.sh`) through an asynchronous GPU readback. The default is `png`.
- `-ncFastForward <speed> [stepFps]`: the skip speed. With `stepFps`, each skipped frame advances the replay by `speed/stepFps` seconds and the game runs as fast as it can.
- `-ncUncapped`: turn off vsync and the frame-rate cap.
- `-ncPerfLog`: log frames per second and replay speed every 5 seconds.
- `-ncPreroll <s>`: seconds before each range that run at normal speed. The default is 1.
- Each finished range writes `<range dir>.done` with the frame count, fps and format.
- `-ncReplayQuit`: quit when the replay or the range ends.
- `-ncStart <seconds>`: start watching at that replay second. The replay skips ahead in fixed steps (8/60 s per frame unless `-ncFastForward` is given) to `seconds - preroll`, then plays at 1x with the normal keys. Pause and the speed keys are ignored while it skips, and the overlay shows "skipping to N s". The log says `Replay start reached`. It is ignored (with a warning) together with `-ncReplayFrames` or `-ncJob`, which have their own ranges. `nr watch --at <s>` passes it. `nr open --at <s>` uses the viewer (`-ncAt`) instead.

Without `-ncShots`, the director uses `<demo>.shots.json` if that file exists.

## Shot lists

```json
{"shots":[
 {"t":0,  "camera":"orbit",   "target":"host", "fov":55},
 {"t":12, "camera":"cockpit", "target":"host"},
 {"t":20, "camera":"chase",   "target":"auto", "hold":3}
]}
```

- `t`: the time in seconds since the demo started.
- `camera`: one of `orbit`, `chase`, `cockpit`, `tv`, `free` or `relative` (the game's own camera states), or one of the cinematic cameras `flyby`, `chase_cine`, `track_from`, `keyframe`, `mount`, `action` and `path` (see "Cinematic cameras" below).
- `target`: one of these:
  - `host`: the hosting player's aircraft.
  - `auto`: follows the host and cuts to each newly launched missile.
  - `latest_missile`
  - `latest_host_missile`
  - `unit:<persistentID>`
  - `name:<substring>`: matches the unit name, for example `name:Revoker`.
  - `none`: only for `path` shots in world space that do not look at a unit; the path starts at once.
- `hold`: the number of seconds the camera stays on a destroyed target. The default is 3. After that, the camera cuts to the live aircraft nearest to where the target died. When a missile followed with one of the game's cameras detonates, the view holds still on the explosion for this time (the game's chase camera would swing to the sky).
- `then`: optional, a shot object (`camera`, `target`, `fov`, `hold`) to cut to once the target is gone and the hold is over, instead of the nearest aircraft. `victim_cut` uses it to cut to the victim at the moment the missile hits: `{"t":29.96, "camera":"chase", "target":"unit:139", "hold":0, "then":{"camera":"orbit", "target":"unit:136", "fov":50}}`. A later shot that repeats the camera and target on screen keeps the camera as it is.
- `fov`: the field of view in degrees. Optional. Note: with the NOVR mod installed, the game cameras ignore `fov` (NOVR blocks every change to `Camera.fieldOfView`). The cinematic cameras work around this.
- `mattes`: optional, for example `["aircraft"]`. Writes an engine matte of the target aircraft for the frames of this shot (see "Engine mattes").

A shot list is plain data, so a person or an agent can write one from narration timestamps. With no shot list, the director uses `orbit` and `auto`.

## Cinematic cameras

These shot types are driven by the replay director itself, not by the game's camera states. Position and aim are smoothed with critically damped springs, the horizon stays level, the camera never goes below terrain or the sea, and the lens can go from wide to very long (2 to 70 degrees). The subject is placed on a third with lead room in its direction of travel unless `frame` says otherwise. Details, all options and limits: `replay/CINE-CAMERA.md`.

```json
{"shots":[
 {"t":0,      "camera":"chase", "target":"host"},
 {"t":1478.6, "camera":"keyframe", "target":"host",
  "keys":[{"t":0,"pos":[-35,-6,80],"fov":40},{"t":3,"pos":[-70,-4,10],"fov":40},
          {"t":6,"pos":[-40,4,-55],"fov":38},{"t":8.6,"pos":[10,4,-60],"fov":36}]},
 {"t":1834.0, "camera":"flyby", "target":"host", "side":"left", "offset":60, "agl":8, "ahead":4.0,
  "track":"/path/to/track.csv", "track_t0":-102.447, "size":0.12, "fov_min":6, "fov_max":35},
 {"t":1842.2, "camera":"track_from", "target":"host", "from":"unit:169", "from_offset":[0,25,0],
  "from_toward":60, "size":0.15, "fov_min":2, "fov_max":25},
 {"t":3046.0, "camera":"chase_cine", "target":"host", "distance":24, "side":8, "height":-4,
  "drift":4, "azimuth":-20, "fov":50, "mattes":["aircraft"]}
]}
```

- `flyby`: the camera is parked beside the target's path a few seconds ahead (`ahead`, default 2.5 s) and pans to follow it as it passes. The pass point comes from `pass` (a global position), from a `track` CSV of the future trajectory (`track_t0` = replay time minus CSV time), or from the current velocity. `side` is `left`, `right`, `below` or `above`; `offset` is the distance from the path in metres; `agl` puts the camera that many metres above the ground. If terrain would hide the path, a nearby spot with a clear line of sight is chosen.
- `chase_cine`: a smooth chase at `distance` behind, `side` to the right and `height` above the target (negative is below), with `lag` seconds of smoothing on the offset and an optional slow orbit `drift` in degrees per second starting at `azimuth`.
- `track_from`: a fixed vantage with a long lens. `from` is a global position `[x,y,z]`, `unit:<id>`, `name:<substring>` or `nearest:<substring>`; a unit vantage moves with the unit. `from_offset` is added to the unit position and `from_toward` moves the camera that many metres toward the target, which keeps the unit's own superstructure and smoke out of frame.
- `keyframe`: a camera path through two or more `keys`. Each key has `t` (seconds into the shot), `pos` (metres, relative to the target's heading as `[right, up, forward]`, or global with `"space":"world"`), an optional `look` point and an optional `fov`. Positions use a Catmull-Rom spline with eased timing.
- `mount`: a close-up camera rigidly attached to the aircraft (GoPro style), riding every roll and bank. `preset` is one of `canopy_front`, `canopy_over_shoulder`, `wing_root`, `wingtip_back`, `belly_gear`, `nozzle` or `weapon_release` (with `weapon`, e.g. `"weapon":"Scimitar"`); `side` is `right` or `left`. Anchors (eye, gear, nozzles, hardpoints, wingtips) are discovered from the airframe. `offset`/`look` (local metres) override the preset, `drift` `[x,y,z]` and `arc` (degrees) add a slow move over `drift_time`. Horizon lock is off by default; the target is drawn at full LOD with the pilot visible, near clip 0.05 m, and the camera is pushed out of the hull. Example: `{"t":2940.6, "camera":"mount", "target":"host", "preset":"weapon_release", "weapon":"Scimitar", "side":"left", "mattes":["aircraft"]}`. Details: `replay/CINE-CAMERA.md`, "Mount close-ups".
- First-person `mount` presets: `pov` (the pilot's eye point looking along the nose, cockpit interior and canopy bow in frame, pilot hidden, fov 50 vertical, about 78 horizontal) and `pov_shoulder` (inside the canopy behind one shoulder; first placement sat behind the headrest, re-tuned but not rendered yet). Options `pitch` (deg), `flightpath` (0-1, turn toward the velocity vector, max 12 deg), `head` (0-1, gentle look into the turn plus G sag), `hud` (experimental, no visible effect in replays). The replay draws no HUD and blank MFDs in first person: the game builds them only for the local player's aircraft. Details: `replay/CINE-CAMERA.md`, "First-person POV".
- Lens options for all four: `fov`, or `size` (auto zoom that keeps the target at that fraction of the frame height) clamped to `fov_min`/`fov_max` with `zoom_smooth` seconds of smoothing. `frame: [x, y]` fixes the screen position of the target (-1 to 1); `lead` (default 0.33) sets the automatic third.
- `action`: a chase camera on a springy arm that reacts to how the aircraft flies: it swings to the outside of a turn, drops back under afterburner, closes in when the aircraft slows and looks into the turn. Options and defaults are in the header of `replay/src/CineAction.cs` (`distance`, `height`, `spring`, `damping`, `look_ahead`, `lead`, `bank`, `roll`, `fov_kick`, `shake` for its own G shake). It is preset 8, "Action cam", in the viewer.
- `path`: a camera path, what Camera Studio writes. `keys` is a list of `{"t", "pos":[x,y,z], "yaw", "pitch", "roll", "fov"}` with `t` in seconds after the shot's `t`. `space` is `world` (global position and compass yaw, the default) or `target` (`pos` in metres right, up and forward of the target in a frame that turns with its level heading, smoothed by `lag` 0.3 s, and yaw relative to that heading). `timing` is `even` (constant speed from the first key to the last, eased by `ease`, default 0.5) or `keys` (reach every key at its time). `aim` is `keys` (the keyed rotations), `target` (look at the target) or `path` (look along the direction of travel), smoothed by `look_smooth`. Positions follow a centripetal Catmull-Rom spline (no loops or overshoot at tight corners), rotations a quaternion spline and the lens a monotone curve; speed counts turning and zooming as well as distance, so a pan on the spot still takes time. The path runs on the replay's clock, so a seek into the shot lands on the same pose. Before the first key the camera waits on it; after the last it holds. `min_agl` defaults to 1 m. Maths: `replay/src/CameraPath.cs`; camera: `CinePath.cs`.
- Shake for every cinematic camera: `handheld` (slow drift and sway, about 0.45 Hz), `rumble` (fast small buzz of a camera fixed to a vehicle, about 15 Hz) and `buffet` (wind on a long lens, about 4.5 Hz in gusts), each 0 (off, the default) to about 3 with 1 the normal strength, and `shake_speed` (1) to scale every frequency. The noise is a function of the replay's time from the shot's start, so a clip renders the same every time (`replay/src/CameraShake.cs`).
- `horizon_lock` is on by default. Set it to `false` and give `roll` in degrees for a Dutch angle.
- Target smoothing for all four: replayed aircraft are placed from 20 Hz network snapshots and wobble about 1 m along their path from frame to frame, which made the jet shake in close shots. The cine camera follows a filtered target (`target_smooth`, default 0.3 s: integrated snapshot velocity, pulled toward the raw position with that time constant; 0 turns it off) and, with `smooth_render` (default true), also draws the target at the filtered position, so jet and camera agree. See `replay/CINE-CAMERA.md`, "Jitter fix".
- Each cine shot writes a per-frame trace of exported frames to `<game>/NuclearReplay/traces/cine_<shot start>_<mode>.csv` (target raw and filtered position, velocity, camera pose, lens, target screen position). `fx/camera/tools/qc.py clip.mp4 <t0> --trace <csv>` reads it.

## Engine mattes

When any shot has `"mattes": ["aircraft"]` and the render uses raw frames (the `scripts/render-clips.sh` fast path), the plugin renders the target aircraft a second time, alone, with the same pose and lens, and writes its silhouette as an 8-bit plane per frame. `render-clips.sh` encodes it as `<clip>_matte.mp4` beside the clip: white is the aircraft, black is everything else, and frames are identical in count and timing to the clip. Ranges with no matte shot get no matte file. The matte ignores occlusion (a jet behind a hill is still white) and does not include exhaust, smoke or other particles. A depth matte is not implemented.

## Headless test runs

`scripts/run-headless.sh` starts Proton directly inside `gamescope --backend headless`, so no window appears on the desktop and focus does not change. Audio is disabled through Wine DLL overrides. The script sets `STEAM_COMPAT_INSTALL_PATH` and `STEAM_COMPAT_LIBRARY_PATHS` so that Proton maps the library to `S:`, as a Steam launch does. The plugin output paths use `S:`. gamescope may segfault on exit after the game quits; this is harmless.

Record test:

```
scripts/run-headless.sh -autoHost -mission "05. Furball" -state SinglePlayer -socket Offline -closeafter 150
```

Nobody flies the aircraft in a headless test, so the host aircraft eventually crashes. The AI fight continues.

## Known limits and untested cases

- Used in real play: human-flown single-player, VR, and multiplayer sessions hosted by the owner with real clients joining (confirmed by the owner, 2026-10-05), including sessions of about an hour. Not yet tested: mission restarts and changes within one session.
- The frame-time cost of the recorder was not measured in a live session. By design it matches one additional remote client.
- A client recording (`[Demo] RecordAsClient`, `src/Demo/ClientDemoRecorder.cs`) stores the messages the server sent that client, from AuthSuccess to disconnect. It rewrites the recorded player's spawns to remote ones, drops owner-only replies and notices, and rebuilds the RPCs and owner sync vars the server never sends back to their owner (missile launches, turret aim, sling loads) from the client's own commands. It holds only what the server shares with players. Tested against a local dedicated server (2026-10-14) with a scripted client that spawned and fired; not yet on a public server, and the recorded player's own flight was not checked in a replay because the test aircraft never left the deck.
- The replay shows the world as a remote observer receives it. Units that the server hides from remote players are hidden in the replay too.
- Client-side cosmetic effects can differ slightly between runs.
- The header's `map_key_type` is written before the map key exists and currently reads `None`. The LoadMap message inside the stream carries the real map.
- Demo files depend on the game version. A game update that changes network messages can make older demos unreadable. The header records `game_version`.

## Version and logs

- The version is set once in `version.props` (`NcVersion`, now 0.5.1). The plugins report the numeric part to BepInEx (`0.5.1`), and the full version in the demo header (`mod_version`) and in the assembly's informational version, which `nr` reads.
- `scripts/package.sh` builds the mod (`NuclearReplay.dll`, both plugins) from source and writes the release zip `NuclearReplay-<version>-plugins.zip` to `dist/` (see `app/RELEASING.md`).
- The plugin log is `<game>/BepInEx/LogOutput.log`. `nr` writes `nuclear-replay.log` in `%LOCALAPPDATA%\Nuclear Replay\logs` or `~/.local/share/nuclear-replay/logs` (rolled at 1 MiB, two old files kept). `nr diagnostics` puts both logs and `nr status` into one text file.
